## Subsystem D — Contract Self-Signup

### Goal
Customers can request a maintenance contract online. Admin reviews, sets price, and activates.

### New contract lifecycle
```
PENDING_REVIEW  →  ACTIVE  →  EXPIRED
                ↓
             CANCELLED
```

### Migration: 018_contract_pending.sql
```sql
ALTER TABLE contracts
  ALTER COLUMN price_sgd SET DEFAULT 0,
  ALTER COLUMN price_sgd DROP NOT NULL,
  DROP CONSTRAINT contracts_status_check,
  ADD CONSTRAINT contracts_status_check
    CHECK (status IN ('PENDING_REVIEW', 'ACTIVE', 'EXPIRED', 'CANCELLED'));

ALTER TABLE contracts
  ADD COLUMN IF NOT EXISTS expiry_reminder_sent boolean NOT NULL DEFAULT false;
```

Notes:
- `price_sgd` becomes nullable — customer requests don't have a price yet (stored as NULL)
- `expiry_reminder_sent` is added here (also needed by Subsystem F) to avoid a second migration
- Existing `ACTIVE`/`EXPIRED`/`CANCELLED` rows are unaffected

### Customer flow: request a contract

**Page:** `/account/contracts` — "Request a Contract" button opens a Dialog

**Form fields:**
- Number of AC units (select: 1–10)
- Service address (pre-filled from `profile.address`; editable Input field — plain text, no geocoding needed)
- Preferred start month (month picker: `<input type="month">`)
- Notes (optional Textarea)
- Pricing hint: auto-show the tier price from `app_settings.contract_pricing_tiers` based on units selected
  - e.g. "For 3 units, estimated price is S$600/year"

**API route: POST /api/contracts/request**
- Authenticated customer only (role check)
- Inserts contract with `status = 'PENDING_REVIEW'`, `price_sgd = NULL`
- Derives `start_date` from selected month (first day of month), `end_date = start_date + 1 year`
- Does NOT generate service dates yet (those happen on activation)
- Returns `{ contract_id }`

### Admin flow: activate a contract

**Where it surfaces:** `/admin/contracts` list — PENDING_REVIEW contracts shown at the top with an amber "Pending Review" badge

**Detail page `/admin/contracts/[id]`:**
- For PENDING_REVIEW status: show a prominent "Activate Contract" CTA (or "Reject")
- Activate dialog fields:
  - Price S$ (pre-filled from tier calculation based on `num_units`)
  - Confirmed start date (pre-filled from customer's requested month)
  - Notes (optional, visible to customer)
- On activate: `PATCH /api/contracts/[id]/activate`
  - Sets `status = 'ACTIVE'`, `price_sgd`, updates `start_date`/`end_date` if changed
  - Generates 4 `contract_service_dates` at 3-month intervals (same logic as existing admin create)
  - Sends `ContractActivated` email to customer

**API route: PATCH /api/contracts/[id]/activate**
- Admin only
- Validates contract is in PENDING_REVIEW state
- Updates fields, inserts service dates, triggers email

### Email: ContractActivated
**Template:** `lib/email/templates/ContractActivated.tsx`
- Subject: "Your maintenance contract is now active — HydroWash"
- Body: Hi [name], your contract for [N] units has been activated. Price: S$[X]/year. Start: [date]. Your first service visit is due [date].

## Subsystem E — Invoice PayNow Payment Display

### Goal
Customers can see how to pay an UNPAID invoice via PayNow. Display a QR code + payment details in the invoice row.

### No migration needed

### New package dependency
Add to `package.json`: `"qrcode.react": "^4.0.0"`

### PayNow QR format
Use the Singapore SGQR / EMVCo format. Build a helper that generates the QR payload string:

```typescript
// lib/utils/paynow.ts
export function buildPayNowPayload(mobile: string, amountSgd: number, ref: string): string
```

The EMVCo TLV format for PayNow mobile:
```
00020101021126[LEN]0009SG.PAYNOW010120212+65XXXXXXXX0301154[LEN]5802SG59[LEN][NAME]6009Singapore54[LEN][AMOUNT]62[LEN]0705[REF]6304[CRC16]
```

CRC16 (CCITT) is required. Implement `crc16ccitt()` in the same util file.
Reference implementation for Singapore PayNow: tag 26 = merchant account (SG.PAYNOW), subtag 01 = proxy type (2=mobile), subtag 02 = proxy value (+65XXXXXXXX), subtag 03 = amount editable (0=no).

### Customer UI: "Pay via PayNow" button on invoice row

**Where:** `app/account/AccountContractsClient.tsx` — each UNPAID invoice row gets a "Pay" button

**Dialog content:**
- Heading: "Pay via PayNow"
- PayNow number: `+65 XXXX XXXX` (large, copyable)
- Amount: `S$[amount]`
- Reference: `HW-[short invoice ID]` (last 8 chars of UUID)
- QR code: `<QRCodeSVG value={payNowPayload} size={180} />` from `qrcode.react`
- Instruction: "Open your banking app, scan the QR code, and transfer S$[amount] with reference [ref]."
- Dismiss button: "Done"

**Note:** No status change — admin marks paid when transfer arrives. Customer just gets the QR.

### Files to create/modify
| File | Action |
|---|---|
| `lib/utils/paynow.ts` | New — `buildPayNowPayload()` + `crc16ccitt()` |
| `app/account/AccountContractsClient.tsx` | Add PayNow Dialog on UNPAID invoice rows |
| `app/account/contracts/page.tsx` | Fetch `app_settings.paynow_mobile`, pass to client |
| `package.json` | Add `qrcode.react` |

### Gotchas
- `qrcode.react` v4 exports `QRCodeSVG` and `QRCodeCanvas` as named exports
- CRC16-CCITT (XModem) must be computed correctly — test `buildPayNowPayload` with a known-good value
- `paynow_mobile` in app_settings may be null → hide PayNow button if null
- If `paynow_mobile` doesn't start with `+65`, strip and reformat

## Subsystem F — Automated Email Reminders

### Goal
Wire up the existing cron jobs to actually send emails. Three email types:
1. Quarterly service visit due (7 days before)
2. Contract expiring in 30 days
3. Day-before booking reminder (already sending — verify it uses `booking_date`)

### No migration needed (expiry_reminder_sent added in 018 for Subsystem D)

### F1: Quarterly service due reminder

**Cron:** `app/api/cron/contracts/route.ts` already flips `reminder_sent = true` for service dates due this month. Wire up the email.

**When to send:** same pass that flips `reminder_sent` — send email immediately after update
**Who to notify:** contract's `customer_id` → get email via `supabase.auth.admin.getUserById`

**Email template:** `lib/email/templates/ContractServiceDue.tsx`
- Subject: "Your quarterly aircon service is due — HydroWash"
- Body: Hi [name], your service visit for contract ([N] units) is due this month ([due_date]). Book your slot at [link to /book].

**What needs fetching:** the cron currently only selects `id` from `contract_service_dates` — expand to select `contract_id, due_date` + join `contracts(customer_id, num_units, address)`.

### F2: Contract expiry reminder

**Cron:** same `api/cron/contracts/route.ts` — currently queries expiring contracts but doesn't email them, and doesn't track `expiry_reminder_sent`.

**When to send:** when `end_date` is within 30 days AND `expiry_reminder_sent = false`
**Action:** send email, set `expiry_reminder_sent = true`

**Email template:** `lib/email/templates/ContractExpiring.tsx`
- Subject: "Your maintenance contract expires soon — HydroWash"
- Body: Hi [name], your contract for [N] units expires on [end_date]. Contact us to renew.

### F3: Day-before booking reminder

**Cron:** `app/api/cron/reminders/route.ts` — already implemented and sending.
**Verify:** it queries `.eq('confirmed_date', tomorrowStr)` — this is WRONG for the new slot model. Should query `.eq('booking_date', tomorrowStr)` (bookings are on `booking_date`, not `confirmed_date`).
**Fix:** change the query to use `booking_date` and `status = 'APPROVED'`.

### Files to create/modify
| File | Action |
|---|---|
| `lib/email/templates/ContractServiceDue.tsx` | New |
| `lib/email/templates/ContractExpiring.tsx` | New |
| `lib/email/send.ts` | Add `sendContractServiceDue`, `sendContractExpiring` |
| `app/api/cron/contracts/route.ts` | Wire up both email sends; use expiry_reminder_sent flag |
| `app/api/cron/reminders/route.ts` | Fix: `booking_date` not `confirmed_date` |

### Gotchas
- Cron runs once per day — both F1 and F2 run in the same cron job file
- `supabase.auth.admin.getUserById` is rate-limited — batch if many customers
- Email failures should not fail the cron — wrap each send in `.catch(() => null)`
- `expiry_reminder_sent` was added in migration 018; F cannot run until 018 is applied

## Subsystem G — Alternative Date Suggestions on Slot Conflict

### Goal
When the customer hits a 409 (slot taken) at booking submission, offer them up to 5 alternative available (date, slot) pairs rather than just showing an error.

### New API: GET /api/availability/suggest

**Query params:** `from=YYYY-MM-DD` (the date that was taken), `slot=S10_12` (the slot that was wanted), `days=14`

**Logic:**
1. Build a set of candidate (date, slot) pairs: all 5 slots × next 14 days starting from `from`
2. Fetch `/api/availability` data for those months (may span 2 months)
3. Filter out: past dates, fully blocked days, slot-blocked slots, already-booked slots
4. Sort by: same slot first (preference), then by date ascending
5. Return top 5 as `[{ date: string, slot: TimeSlot }]`

**Auth:** unauthenticated (same as `/api/availability`)

### BookingWizard changes

After `POST /api/bookings` returns 409:
1. Display error: "That slot was just taken."
2. Fetch `GET /api/availability/suggest?from=[booking_date]&slot=[time_slot]`
3. If suggestions returned, show below the error:
   - Heading: "Available alternatives"
   - Up to 5 pills: `[date label] · [slot label]` (e.g. "Tue 20 May · 13:00 – 15:00")
   - Clicking a pill: `update({ booking_date: date, time_slot: slot })`, navigate back to step 1 (setStep(1))
4. If no suggestions: "No nearby slots available — please pick another date from the calendar."

### Files to create/modify
| File | Action |
|---|---|
| `app/api/availability/suggest/route.ts` | New — GET with `from`, `slot`, `days` params |
| `components/booking/BookingWizard.tsx` | Handle 409 → fetch suggestions → render pills |

### Gotchas
- Suggestions may span two calendar months — fetch availability for both months and merge
- The suggestion fetch happens only after a 409, not on every render — no extra load
- Clicking a suggestion pill should also close the error state (clear `error`)
- `StepScheduleLocation` doesn't need changes — it already responds to `data.booking_date`/`data.time_slot` changes; navigating to step 1 re-renders it with the new values
